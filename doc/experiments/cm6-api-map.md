# The old editor's API and its CodeMirror 6 equivalents

The old editor (`packages/codemirror-blocks`, CM5 + React) offered one entry point, `CodeMirrorBlocks(...)`, which returned a wrapper (`API`, in `src/CodeMirror-api.tsx`) holding the CM5 methods plus a few block methods. The decision is that the CM5 spellings are no longer needed, but their CM6 equivalents should exist on the experiment (`createLezerBlockEditor` in `packages/cm6-blocks/src/lezer-view.ts`, the `ed` object; also `mode.ts` and `lang-*.ts`).

Source of the list: `CodeMirrorBlocks.tsx`, `CodeMirror-api.tsx` (the `codeMirrorAPI` array, `unsupportedAPIs`, `BlockModeAPI`, `ToggleEditorAPI`), `languages/index.ts`, `announcer.ts`, and the 40 rows of `e2e/ported-blockers.csv` with dependency `EXCLUDED-N`. The old README and `doc/` do not document `getTheme`, `loadTemplates`, `saveDocument`, `setAnnouncer`, `renderOptions`, `onChange` or `onBeforeChange` as wrapper methods: they do not exist in the old source (`onChange`/`onBeforeChange` were internal CM5 handlers in `BlockEditor.tsx`; `say`/`mountAnnouncer` were module functions). They are listed at the end as "not an API".

Status: ALREADY HAVE (an `ed` member or a CM6 one-liner does it) / EASY (under about 30 lines) / MEDIUM / HARD or NOT SENSIBLE. "Tests" are the EXCLUDED-N ports the row would un-skip (a test needing two rows is counted on the main one).

## Status counts

Rows by status (the grouped rows counted once each): ALREADY HAVE 19, EASY 21, MEDIUM 11, HARD 1, NOT SENSIBLE 10, NOT AN API 2 (64 rows in all).

## Recommended order (cheapest, most tests first)

1. Promote the compat shim (`spec/compat/api.ts`) into `src/` as the one facade (stable object, same object in both modes, block-only methods throw in text mode): covers the facade rows and their 9 entry-point tests together with step 2.
2. A language registry (`addLanguage`/`getLanguage`/`getLanguages`/`removeLanguage`) and the same-container `WeakMap`: 3 of the entry-point tests.
3. `markText` field plus `findMarks`, `findMarksAt`, `getAllMarks`, `clear`/`find`: 15 tests with about 100 lines (most tests for one piece of machinery).
4. `setValue` focus rule, `replaceRange`/`replaceSelection`/`getCursor`/`setCursor`/`somethingSelected` promoted from the compat layer with the throwing cases: 3 + 4 tests.
5. `extendSelection*` (block-boundary rule): 3 tests.
6. `setBookmark` (shares the mark field): 1. `setBlockMode` named in the facade: 1.
7. Then, only if wanted: `on`/`off` (`updateListener`, `transactionFilter`), `getOption`/`setOption` through a `Compartment`, `markClean`/`isClean`, the CM5 metric methods.

Leave alone: `runMode`, `getLineHandle`, `operation`, `findPosH/V`, `execCommand`, `getHistory`/`setHistory`, the React node kit. The `runMode` and `getLineHandle` tests should be rewritten as "not supported" tests or deleted.

## Needs a design decision

1. **Should the facade live in `src/` as a public module (a CM5-shaped object over `ed`), or should the CM6 editor keep `ed` as its API and only the tests keep a shim?** Recommend a small public `createBlocks(...)` facade in `src/`, built from the compat layer, because the entry-point tests (9) and `setValue`/`markText` tests exist to check exactly that surface.
2. **Positions: keep `{line, ch}` on the facade, or offsets?** Recommend `{line, ch}` on the facade (the ports use them) and offsets on `ed`.
3. **Marks: are they only on whole blocks, as before (options `css`, `className`, `title`), or any range, as CM6 allows?** Recommend keep the old restriction (the tests assert it) and make it one check.
4. **Do marks belong to the block (they die with it) or to the text range (they move with the text)?** The ports want both: the field maps through changes and an empty range is dropped. Recommend that, so no persistent block ids are needed.
5. **CM6 extensions as the replacement for `codemirrorOptions`: add an `extensions` option, and a `Compartment` for `getOption`/`setOption`?** Recommend yes for `extensions`, no for `setOption` (offer `ed.reconfigure(ext)` instead).
6. **Events: do we offer `on`/`off` with CM5 names, or only CM6 `updateListener`s?** Recommend CM6 only through `ed.view`, plus `ed.onModeChange`; no ported test needs it.
7. **`runMode` and `getLineHandle`: refuse (throw), or leave out?** Recommend leave out and rewrite the two tests.
8. **Block-only methods in text mode: throw (as before) or return empty answers?** Recommend throw, since the tests assert it.

## What a CM6 user can call today

Decisions of 2026-11-23 replace the recommendations above where they differ: the goal is that a CodeMirror 6 user who embeds this editor instead of plain CodeMirror 6 changes no supported call. There is no CodeMirror 5 facade, no `{line, ch}`, no CM5 event names, no `setOption`, no `runMode` or `getLineHandle` (CM6: `state.doc.line(n)`; `highlightTree` of `@lezer/highlight`; nothing else in the map is missing). Block-only methods stay on the editor and throw in text mode where they have no answer.

How a user gets the editor: `createLezerBlockEditor({parent, doc, extensions, parser, table, ...})` (or the older `(host, text, options)`), then uses the returned object `ed` as the `EditorView`. `ed.view` is still the real `EditorView`.

## Decisions (user, 2026-11-23)

- **Block methods in text mode.** Only the methods that read the block tree (`roots`, `focusedNode`, `selection`, `selectedBlocks`) throw "only available in block mode" in text mode. The methods that change text by block (`insertText`, `removeNode`, ...) are plain text changes and keep working in text mode.
- **`setState`.** No block-aware `ed.setState`. A state made elsewhere lacks the block field and is unsupported; replacing the document is `ed.dispatch({changes})`.
- The CM5 API is not supported; the CM6 API is the supported surface (see the audit section above). No language registry (a language is its parser and table, imported directly).
